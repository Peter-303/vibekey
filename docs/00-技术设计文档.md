## 0. 与 PRD 的差异清单（先看这里）

本文档对 PRD 做了 6 处**补充**和 1 处**收紧**，都是 PRD 留空或存在漏洞的地方。每处都标了理由，需 owner 确认：

| # | PRD 原文 | 本文档裁定 | 理由 |
|---|---|---|---|
| 1 | 5.4 "一次按下只发一次字符；长按不连发" | **保留，但新增 TYPE 0x05 按键释放帧（默认关闭）** | 见 §5.4：语音流式模式"按住说话、松开结束"需要释放沿，只有按下事件无法实现。这是 PRD 的真实缺口。 |
| 2 | 7 章 "上位机任一条收到都可处理，去重策略由上位机负责（建议按帧序号去重）" | **同一事件在 USB/WiFi 两条通道上必须共用同一个 SEQ 值** | PRD 没说清。若两条通道各自生成 SEQ 必然撞号，去重完全失效。见 §3.4。 |
| 3 | 5.2 / 6.2 未定义 STA 模式下 PC 如何获知设备 IP | **UDP 广播发现为主，mDNS 为可选补充** | PC 连的是路由器，设备 IP 由 DHCP 分配。没有发现机制，用户每次都要查路由器后台。见 §4.2。 |
| 4 | 5.1 "所有状态切换必须与上位机心跳上报的状态码一致" vs 5.6 "ASR 不可用时只报 WARN 不改灯" | **状态码与警告码分离：状态驱动 LED，警告只是上报字段** | PRD 两处要求冲突。见 §5.1。 |
| 5 | 5.5 "烧录态唯一入口：magic word + 超时窗口" | **收紧为：magic word + 仅 USB 通道 + 5s 内一次性有效 + 设备须处于非 ERROR 态** | PRD 说"WiFi 报文不能触发烧录态"但没写实现约束。明确写成通道级拒绝，比报文级判断更可靠。见 §7.1。 |
| 6 | 5.6 "本地缓存整段音频（环形缓冲）" | **60s 音频 = 1.92 MB，ESP32-S3 内部 RAM 放不下，必须落 PSRAM** | PRD 未评估内存量级。见 §5.5。 |
| 7 | 5.3 UART1 帧格式 | **统一为 `STATUS:<STATE>[,<KEY>=<VAL>]*\r\n`，USB/WiFi 的 0x02 载荷为去掉 `STATUS:` 前缀的同一字符串** | PRD 要求 0x02 "与 UART1 一致"但没定义一致到什么程度。这样定义后两边共用一个序列化函数。见 §3.5。 |

## 2. 总体架构

### 2.1 下位机分层（核心约束：应用层与移植层彻底分离）

```
┌─────────────────────────────────────────────────────────┐
│  app/  应用层 —— 纯 C99，零 ESP-IDF 依赖                  │
│         可在 PC 上用 gcc/clang 编译并跑单元测试            │
│                                                          │
│  app.c          主调度：把 port 收到的东西分发给各状态机    │
│  proto.c        帧编解码（USB/WiFi 共用，SEQ 唯一来源）    │
│  led_fsm.c      状态码 → LED 表现                          │
│  key_fsm.c      原始电平采样 → 去抖 → 事件字符（纯函数）     │
│  net_fsm.c      AP/STA/NVS 配网状态机                      │
│  asr_fsm.c      语音会话状态机                             │
│  cmd_dispatch.c 下行指令分发 + magic word 校验              │
│  seq.c          SEQ 分配器（单调递增，跨通道一致）           │
│  status.c       状态码/警告码字符串表                       │
├─────────────────────────────────────────────────────────┤
│  port.h  移植层接口 —— 应用层唯一依赖的外部符号             │
│          一个 const port_t 函数指针表，main.c 启动时注入    │
├─────────────────────────────────────────────────────────┤
│  port_esp32.c   ESP-IDF 实现（GPIO/UART/TinyUSB/WiFi/NVS） │
│  port_board.h   ★ GPIO 引脚宏，硬件变动只改这一个文件        │
└─────────────────────────────────────────────────────────┘
```

**为什么这样做**：用户已明确"移植层后面会有变动"。因此：

- `port.h` 是**唯一**的硬件依赖面。应用层代码 `#include` 的 ESP-IDF 头文件数量为 **0**。
- `port_t` 用函数指针表注入，不用弱符号、不用条件编译散落各处。换硬件 = 换一个 `port_xxx.c` + 改 `port_board.h`。
- 应用层的每个状态机都是**纯函数式**的：输入是采样值和时间戳，输出是事件。这让它可以在 PC 上被完整单测，**不等硬件就能验证按键消抖、协议编解码、状态机迁移**——直接支撑 M1 在无板阶段就能完成大部分工作。
- `test/` 目录用 `port_stub.c` 提供假实现，与固件共用同一份 `app/` 源码编译。

### 2.2 上位机分层

```
Views/            WPF 页面（设备状态 / 按键映射 / 语音 / 烧录 / 设置）
ViewModels/       MVVM（CommunityToolkit.Mvvm）
Services/
  IDeviceTransport    通道抽象：UsbCdcTransport / WifiTcpTransport / SimulatedTransport
  FrameCodec          与固件 proto.c 逐字节一致的编解码（同一组测试向量）
  DeviceSession       心跳、SEQ 去重、状态缓存
  MappingStore        %AppData%/VibeKey/mappings.json，导入导出
  ActionExecutor      文本 / 快捷键 / 打开程序或URL / 语音 / 剪贴板
  Flasher             ESP32 ROM 串行烧录协议（C# 原生实现，不依赖 Python）
  AutoStartService    HKCU\...\Run 开机自启
Models/
```

**关键点**：`IDeviceTransport` 让 `SimulatedTransport`（模拟设备）与真实 USB/WiFi 传输**走同一条代码路径**。上位机从 M1 起就能完整开发 UI 和映射逻辑，不需要等硬件。

## 3. 通信协议（已冻结）

### 3.1 帧格式

```
┌──────┬──────────┬──────┬──────────┬─────────────┬──────────┐
│ 0xAA │ LEN(2B)  │ TYPE │  SEQ(2B) │  PAYLOAD    │ CRC16(2B)│
│  1   │   LE     │  1   │   LE     │  LEN bytes  │   LE     │
└──────┴──────────┴──────┴──────────┴─────────────┴──────────┘
   0        1        3        4          6        6+LEN
```

| 字段 | 偏移 | 长度 | 定义 |
|---|---|---|---|
| SOF | 0 | 1 | 固定 `0xAA` |
| LEN | 1 | 2 | **PAYLOAD 字节数**（不含帧头、CRC）。小端。范围 0–1024 |
| TYPE | 3 | 1 | 帧类型，见 §3.3 |
| SEQ | 4 | 2 | 帧序号，小端。上行由设备分配，下行由上位机分配，见 §3.4 |
| PAYLOAD | 6 | LEN | 载荷 |
| CRC16 | 6+LEN | 2 | 小端。覆盖范围 = 字节 1 .. 6+LEN-1（即 LEN+TYPE+SEQ+PAYLOAD），**不含 SOF，不含 CRC 自身** |

**冻结参数：**
- 字节序：一律**小端**（little-endian）。
- CRC 算法：**CRC16/CCITT-FALSE** —— 多项式 `0x1021`，初始值 `0xFFFF`，输入输出**不反射**，异或值 `0x0000`。
- 最大载荷：**1024 字节**。超过则上层必须分片（ASR 文本按句切分，不会超）。
- 最小帧长：8 字节（LEN=0）。
- 无转义、无字节填充。载荷为二进制安全的原始字节；解析端按 LEN 定长读取，不扫描分隔符。
- 接收端失步恢复：丢弃当前字节，重新扫描 `0xAA`。

### 3.2 TYPE 分配表（已冻结）

| TYPE | 方向 | 名称 | PAYLOAD 定义 |
|---|---|---|---|
| `0x01` | 上行 | 按键/旋钮事件 | 1 字节 ASCII 字符，见表 §4 |
| `0x02` | 上行 | 状态上报 | 状态字符串，格式见 §3.5 |
| `0x03` | 上行 | ASR 文本 | 首字节 `0x00`=中间结果 / `0x01`=最终结果，其余为 UTF-8 文本 |
| `0x04` | 上行 | 心跳 pong | 空（状态由 0x02 事件驱动推送） |
| `0x05` | 上行 | 按键释放 | 1 字节 ASCII 字符。**默认不发送**，见 §5.4 |
| `0x06` | 上行 | 指令应答 ACK/NACK | 首字节 `0x00`=ACK / `0x01`=NACK；若 NACK，第 2 字节起为 ASCII 原因码 |
| `0x10` | 下行 | 心跳 ping | 空 |
| `0x11` | 下行 | 下发 WiFi 配置 | `SSID\0PASSWORD\0`（两个 C 字符串，各含结尾 `\0`） |
| `0x12` | 下行 | 下发 ASR 配置 | `KEY=VALUE\0KEY=VALUE\0...\0`，键见 §5.5 |
| `0x13` | 下行 | 进入烧录模式 | 8 字节 magic word，见 §7.1 |
| `0x14` | 下行 | 语音启停 | 1 字节：`0x01`=开始 / `0x00`=停止 |
| `0x15` | 下行 | 请求立即上报状态 | 空 |
| `0x16` | 保留 | — | 预留给通用 KV 读写，本期不用 |
| `0x7F` | 双向 | 协议版本协商 | PAYLOAD = `VER=1`，连接建立后双方各发一次 |

> `0x14` 是本文档新增的（PRD 未定义）。原因：语音模式切换需要上位机能显式开始/停止录音会话，否则只能靠"再按一次语音键"隐式切换，用户无法从界面直接打断。需 owner 确认。
> `0x16`、`0x7F` 为占位，避免后期加类型时与已冻结值冲突。

### 3.3 示例帧（可直接作为测试向量）

**① 按键 K1 按下（上行）** — 字符 `'1'`，SEQ=1
```
AA 01 00 01 01 00 31 46 2C
```
逐字节：`AA` | LEN=`01 00`→1 | TYPE=`01` | SEQ=`01 00`→1 | PAYLOAD=`31`('1') | CRC=`46 2C`→0x2C46

**② 心跳 ping（下行）** — SEQ=1000
```
AA 00 00 10 E8 03 17 FB
```
逐字节：`AA` | LEN=`00 00`→0 | TYPE=`10` | SEQ=`E8 03`→1000 | 无载荷 | CRC=`17 FB`→0xFB17

**③ 状态上报（上行）** — `WORK_READY,FW=1.0.0,RSSI=-58`，SEQ=7
```
AA 1C 00 02 07 00 57 4F 52 4B 5F 52 45 41 44 59 2C 46 57 3D 31 2E 30 2E
30 2C 52 53 53 49 3D 2D 35 38 68 D0
```
逐字节：`AA` | LEN=`1C 00`→28 | TYPE=`02` | SEQ=`07 00`→7 | PAYLOAD=ASCII×28 | CRC=`68 D0`→0xD068

以上三组已用 CRC16/CCITT-FALSE 实算校验，`test/test_proto.c` 与 `host` 的 `FrameCodecTests` **必须原样通过**。

### 3.4 SEQ 规则与双通道去重（对 PRD 的关键修正）

**规则 1** — 上行 SEQ 由设备侧 `seq.c` 统一分配，**单调递增，16 位回绕**。每次"产生一个上行帧"取一个号，与即将通过几条通道发送无关。

**规则 2** — 当一个事件需要同时走 USB 和 WiFi 时，**两条帧使用完全相同的 SEQ**。也就是：先分配 SEQ，再用同一个 SEQ 构造两条帧。

**规则 3** — 上位机维护 `last_seq`（按来源通道分别记录，但比对时取两者较大值的跨通道视图）。收到 SEQ ≤ 已见最大值 → 判定为重复帧，丢弃。

**规则 4** — 下行 SEQ 由上位机分配，设备回 `0x06` ACK 时**原样带回该 SEQ**。上位机未收到匹配 ACK 超时 2s 可重发，重发使用**新的 SEQ**（避免与旧帧混淆）。

> 为什么规则 2 重要：PRD 只说"按帧序号去重"。如果两条通道各自生成 SEQ，设备可能几乎同时发出 USB:SEQ=100 和 WiFi:SEQ=100 两个**不同**事件，上位机按 SEQ 去重会误删真实事件。共用 SEQ 后，去重键就是事件本身，语义正确。

### 3.5 状态上报字符串格式

```
<STATE>[,<KEY>=<VAL>]*
```

- 与 UART1 的关系：UART1 发的行是 `STATUS:` + 上述字符串 + `\r\n`；USB/WiFi 的 `0x02` 载荷就是上述字符串本身（无前缀）。**两边共用同一个 `status_format()` 函数**，保证 PRD 要求的"与 UART1 一致"。
- 分隔符为 `,`。所有取值中不得出现 `,` 或 `=`（SSID 含逗号时设备侧拒绝并回 NACK，需在上位机配网页校验）。

**必须出现的字段**（可扩充）：

| 键 | 必填 | 示例 | 说明 |
|---|---|---|---|
| `STATE` | ✅ | `WORK_READY` | 状态码，见 §5.1 |
| `FW` | ✅ | `1.0.0` | 固件版本，编译期注入 |
| `RSSI` | STA 态 | `-58` | WiFi 信号强度 |
| `IP` | STA 态 | `192.168.1.23` | |
| `SSID` | AP 态 | `VibeKey-1A2B` | 自身热点名 |
| `ERR` | 有则填 | `MIC_FAIL` | 最近故障码 |
| `WARN` | 有则填 | `ASR_UNAVAILABLE` | 警告码，**不改变 LED** |
| `ASR` | 有则填 | `OK` / `BUSY` / `DOWN` | 语音模块状态 |
| `CH` | 有则填 | `USB+WIFI` | 当前活跃通道 |

## 4. 按键字符表（7 键 + 编码器 = 10 事件，已冻结）

PRD 5.4 要求"具体每颗物理键映射到哪个字符码，硬件布局定稿后由固件冻结"。硬件输入已定为 **7 键 + 1 编码器**，字符表冻结如下：

| 输入 | 字符 | ASCII | 备注 |
|---|---|---|---|
| 机械键 K1 | `1` | 0x31 | |
| 机械键 K2 | `2` | 0x32 | |
| 机械键 K3 | `3` | 0x33 | |
| 机械键 K4 | `4` | 0x34 | |
| 机械键 K5 | `5` | 0x35 | |
| 机械键 K6 | `6` | 0x36 | |
| 机械键 K7 | `7` | 0x37 | **建议默认绑定为语音键**（见下） |
| 编码器 顺时针 | `+` | 0x2B | |
| 编码器 逆时针 | `-` | 0x2D | |
| 编码器 按下 | `0` | 0x30 | 等同普通按键 |

**选字符的理由**：
1. 全部是可打印 ASCII，串口助手里直接肉眼可读，不需要查表——这对 M1 联调价值很大。
2. `1`–`7` 与物理键序号一一对应，看串口就知道按的是第几颗。
3. 与常见文本字符无冲突风险，因为按键字符**只在协议层作为标识符**，永远不会被当作文本输入到系统（翻译全在上位机）。
4. 编码器三个动作用 `+`/`-`/`0`，语义直观。

**语音键**：固件**不需要知道**哪颗是语音键——这是上位机映射层的事。但建议出厂默认映射把 K7(`7`) 绑到"触发语音输入"，与产品定位一致。若启用 §5.4 的释放帧，也只有这颗键的释放会被上报。

> 若硬件最终回到 6 键，只需从本表删除 `7` 一行，`key_fsm` 与上位机映射 UI 均按输入数量自适应，**不改协议**。

## 5. 下位机状态机设计

### 5.1 状态码与警告码分离（对 PRD 冲突的裁决）

**状态码**（7 个，驱动 LED，与心跳一致）：

| 状态码 | 值 | 蓝灯 | 红灯 | 进入条件 |
|---|---|---|---|---|
| `BOOT` | 0x01 | 常亮 | 常亮 | 上电即进入，初始化结束即离开（≤2s） |
| `AP_START` | 0x02 | 红蓝交替闪 | 红蓝交替闪 | NVS 无凭据，或 STA 重试达上限回退 |
| `STA_JOIN_OK` | 0x03 | 常亮 | 灭 | STA 关联成功、拿到 IP |
| `STA_JOIN_FAIL` | 0x04 | 灭 | 慢闪×3 后转 AP | STA 单次尝试失败（瞬态，非故障） |
| `WORK_READY` | 0x05 | 常亮 | 灭 | 主循环就绪，服务端口已监听 |
| `ERROR` | 0x06 | 灭 | 常亮 | 不可恢复错误，见下表 |
| `DOWNLOAD` | 0x07 | bootloader 决定 | bootloader 决定 | 收到合法 `0x13`，`esp_restart()` 前瞬态上报 |

`ERROR` 的故障码（`ERR=` 字段）：`WIFI_FAIL`、`MIC_FAIL`、`ASR_INIT_FAIL`、`USB_FAIL`、`NVS_FAIL`、`WDT_RESET`。

**警告码**（只是 `0x02` 的 `WARN=` 字段，**完全不改变 LED**）：

| 警告码 | 触发 | 上位机表现 |
|---|---|---|
| `ASR_UNAVAILABLE` | ASR 服务不可达 / Key 失效 / 无外网 | 语音区显示"语音不可用"，按键仍可用 |
| `RSSI_LOW` | RSSI < -80 dBm | 状态卡黄点提示 |
| `MIC_DEGRADED` | 采集到连续静音超限 / 底噪异常 | 语音区提示 |

> 这条直接解决了 PRD 5.1 与 5.6 的矛盾：ASR 不可用时 LED 保持 `WORK_READY` 的蓝灯常亮，只把 `WARN=ASR_UNAVAILABLE` 报上去。**状态机只有 7 个态，不会因为附加功能而膨胀。**

### 5.2 配网状态机（AP/STA/NVS）

```
                    ┌──────────────────────────────┐
                    ▼                              │
        [BOOT] ──读 NVS──┬─ 有凭据 ──▶ [STA 尝试]   │
                         │                          │
                         └─ 无凭据 ──▶ [AP_START]◀──┘ (重试 3 次耗尽)
                                        │
                                上位机下发 0x11
                                        │
                              写 NVS ──▶ esp_restart()
                                        │
                    ┌───────────────────┴──────────┐
                    ▼                              ▼
            [STA_JOIN_OK] ──▶ [WORK_READY]   [STA_JOIN_FAIL] ──▶ [AP_START]
```

**冻结参数**（PRD 给的是建议值，此处定稿）：

| 参数 | 值 | PRD 建议值 |
|---|---|---|
| STA 单次超时 | 10 s | 10s ✅ |
| STA 重试次数 | 3 | 3 ✅ |
| 重试间隔 | 2 s（PRD 未定义，此处补充） | — |
| AP SSID | `VibeKey-` + MAC 后 4 位大写 | ✅ |
| AP 密码 | 见 §7.2 | 建议 8 位以上随机串 ✅ |
| AP 加密 | WPA2-PSK | ✅ |
| 回退行为 | 重试耗尽 → `AP_START`，**不进入 ERROR** | PRD 5.2 已明确"不死机、不红灯常亮" ✅ |
| 0x11 写入时机 | **先完整收帧并校验 CRC，再写 NVS，最后才重启** | PRD 8 章"没写完就断开 → NVS 不写半成品" ✅ |

**拔路由器场景**：已 `WORK_READY` 时路由器断开 → 重试窗口（约 36s）内持续尝试 → 耗尽回退 `AP_START`。全程**不进入 ERROR、不红灯常亮**。

### 5.3 按键事件状态机（消抖，纯函数）

应用层收到的是 `port` 送来的**原始电平采样**，不直接收中断——这样消抖逻辑可完整单测。

```
每个输入维护：
  stable_state   当前确认的电平（0=释放, 1=按下）
  last_change_ms 最后一次电平跳变的时刻
  pending        未确认的电平

每 5ms 采样一次（port 层提供 tick）：
  若 sample != pending:
      pending = sample; last_change_ms = now
  否则若 pending != stable_state 且 (now - last_change_ms) >= DEBOUNCE_MS:
      stable_state = pending
      ▶ 若变为 1 → 发射按下事件（分配 SEQ，构造 0x01 帧）
      ▶ 若变为 0 → 若释放帧已启用，发射 0x05 帧
```

| 参数 | 冻结值 | PRD 要求 |
|---|---|---|
| 消抖时间 | **15 ms** | 10–20ms ✅ |
| 采样周期 | 5 ms | PRD 未定义，此处补充 |
| 长按连发 | **禁止** | PRD 明确要求 ✅ |
| 一次按下 | 恰好 1 个 `0x01` 帧 | ✅ |

**编码器**（A/B 相）：
- 采样周期同样 5ms，对 A、B 两相**分别**做 15ms 消抖（相位消抖）。
- 用 4 态格雷码状态机判定方向，**每个机械档位（detent）恰好产出 1 个事件**，避免"旋转一格出两个方向事件"（PRD 5.4 明确要求）。
- 编码器按下 = 普通按键，走同一条消抖路径。
- 不实现 PRD 早期版本提到的"转速补偿/加速"——本期不需要，且会增加误触发面。**建议从范围中移除。**

### 5.4 按键释放帧（`0x05`）—— 本文档新增，需 owner 确认

**问题**：PRD 5.6 的流式模式定义为"用户**按住**语音键说话，**松开**后给出最终结果"。但 PRD 5.4 又规定"一次按下只发一次字符；长按不连发"——固件只有按下事件，**无法知道用户何时松手**，流式模式的"松开即结束"无法实现。

**三种方案**：

| 方案 | 做法 | 评价 |
|---|---|---|
| A | 上位机收到语音键字符后，把交互改成"点一下开始、再点一下结束" | 最小改动，但违背 PRD 的"按住说话"产品定义，手感差异明显 |
| B | 固件对**语音键**额外上报释放帧（`0x05`），其他键不上报 | 保留产品定义；固件需知道哪颗是语音键（一个 NVS 配置项） |
| C | 所有键都上报释放帧，由上位机决定是否使用 | 最灵活，帧量翻倍 |

**裁定：方案 B。** `0x05` 帧默认**不发送**（`CONFIG_VIBEKEY_SEND_KEY_RELEASE` 默认 n），仅在语音键上、且仅当 `NVS: voice_key_enabled = 1` 时启用。这样：
- 不违背 PRD"长按不连发"（释放帧是不同类型帧，不是重复字符）。
- 帧量几乎不变。
- 语音键是哪颗，由上位机在配网时一并写入 NVS，固件不写死。
- 上位机的 `0x14` 语音启停指令作为兜底：即使没有释放帧，用户也能从界面停止录音。

### 5.5 语音会话状态机

```
IDLE ──(0x14 start 或 语音键按下)──▶ CAPTURING
CAPTURING ──(松开 / 0x14 stop)──▶ UPLOADING
CAPTURING ──(mic 错误)──▶ ERROR(MIC_FAIL)
UPLOADING ──(ASR 返回)──▶ IDLE（文本已通过 0x03 发出）
UPLOADING ──(ASR 失败)──▶ IDLE + WARN=ASR_UNAVAILABLE（不进入 ERROR）
```

**ASR 配置项**（`0x12` 帧的键，全部落 NVS）：

| 键 | 必填 | 示例 |
|---|---|---|
| `provider` | ✅ | `tencent` / `volcano` |
| `appid` | ✅ | |
| `secret_id` | ✅ | |
| `secret_key` | ✅ | |
| `sample_rate` | ✅ | `16000` |
| `format` | ✅ | `pcm` |
| `channels` | ✅ | `1` |
| `voice_key` | ✅ | `7`（哪颗键是语音键，配合 §5.4） |

**音频参数冻结**：16 kHz / 16 bit / 单声道 PCM。码率 32 KB/s。

**整包模式内存（对 PRD 的修正）**：PRD 说"本地缓存整段音频（环形缓冲）"，但未评估容量：
- 60 s × 16000 × 2 B = **1.92 MB**
- ESP32-S3-WROOM-1 内部 SRAM 约 512 KB，**放不下**。

**裁定**：整包缓冲必须落在 **PSRAM**（`heap_caps_malloc(..., MALLOC_CAP_SPIRAM)`），并在编译期检查 `CONFIG_SPIRAM` 已启用；若模组无 PSRAM，则整包模式降级为"边采边传"（流式通道上传，上位机侧拼接）。此约束需在 BOM 阶段确认模组是否带 PSRAM——**这是一个新的硬件依赖，需 owner 确认**。

### 5.6 看门狗

- 使能 TWDT，超时 10s，主循环每轮喂狗。
- `esp_restart()`（配网写入后 / 进入烧录）前：**必须**先 `nvs_commit()` 完成、注销 TWDT 或确认不在 TWDT 临界区，再重启。
- 启动时若检测到上一次复位原因为 `ESP_RST_PANIC`/`ESP_RST_TASK_WDT`，先通过 UART1 报 `STATUS:ERROR,ERR=WDT_RESET`，然后按上次状态尝试恢复（有 NVS 凭据则试 STA，否则 AP）。

## 6. 通道模型

### 6.1 USB CDC（主通道）

- TinyUSB CDC-ACM，虚拟 COM 口。Windows 10 1809+ / 11 自带 `usbser.sys`，**安装包不携带任何驱动、不申请驱动签名**。
- 上位机按 **VID/PID** 枚举识别，再映射到 COM 口名。多设备场景本期不支持，但 UI 必须提供手动选 COM 口兜底。
- 断线重连：上位机监听 `WM_DEVICECHANGE`，设备移除即标记离线，重新出现即自动重连，**不要求用户拔插**。

### 6.2 WiFi TCP + UDP 发现（辅通道）

| 项 | 冻结值 |
|---|---|
| TCP 服务端口 | **8266**（`CONFIG_VIBEKEY_TCP_PORT`） |
| UDP 发现广播端口 | **8267**（`CONFIG_VIBEKEY_DISCOVERY_PORT`） |
| 发现协议 | 上位机向 `255.255.255.255:8267` 广播 `VIBEKEY_DISCOVER\r\n`；设备回 `VIBEKEY_HERE,IP=<ip>,MAC=<mac>,FW=<ver>\r\n` |
| 广播周期 | 上位机搜索期间每 500ms 一次，收到首个响应即停 |
| mDNS | 可选补充（`_vibekey._tcp`），本期不强制，因为 Windows 需 Bonjour 才解析 `.local` |

**AP 模式下**：PC 已连设备热点，直接连 `192.168.4.1:8266`，无需发现。
**STA 模式下**：靠 UDP 广播发现拿到 IP 再连 TCP。这是 PRD 缺失的一环，本节补齐。

### 6.3 双通道优先级与去重

- 按键事件、ASR 文本、状态上报：**USB 与 WiFi 同时发送**（同一 SEQ，见 §3.4）。
- 下行指令（`0x11`~`0x15`）：**只走 USB**。其中 `0x13` 烧录指令**只接受来自 USB 的**，WiFi 收到直接回 NACK（见 §7.1）。
- 上位机侧：任一条通道收到即处理，按 SEQ 跨通道去重。心跳 ping 只走当前"主通道"（USB 优先），避免双通道心跳互相干扰。

## 7. 安全边界

### 7.1 烧录态唯一入口（收紧）

PRD 5.5 要求 magic word + 超时窗口。本文档收紧为**四个条件同时满足**才执行 `esp_restart()` 进下载模式：

1. **帧类型为 `0x13`** 且 CRC 校验通过；
2. **载荷 8 字节与 magic word 逐字节相等**；
3. **来源通道必须是 USB CDC**——WiFi TCP 收到的 `0x13` 一律丢弃并回 NACK，不进下载模式；
4. **一次性有效**：同一 magic word 被接受过一次后，5 秒内再次收到同值直接忽略（防止重放）；设备须处于非 `ERROR` 态。

**magic word 冻结值**：
```
56 49 42 45 46 4C 41 53    ("VIBEFLAS")
```
> 说明：这是**混淆而非安全机制**——固件开源，任何人可从源码读出。其真实作用是防止普通业务报文、串口误触、日志噪声意外触发下载模式。真正的人员侧防护是上位机的二次确认弹窗（PRD 6.3 已要求）。若后续要提高到真实安全级别，需改为 challenge-response + 设备侧私钥，本期不做。

**端口跳变（必须在技术文档写明的坑，PRD 未提）**：

> **先纠正一个容易搞错的前提**：ESP32-S3 的 USB-OTG 与 USB Serial/JTAG **共用同一对物理引脚**
> GPIO20(DP) / GPIO19(DM)。它们不是两个可以分别布线的东西——USB-C 的 D+/D- 只要接到
> GPIO19/20，两个外设就都连在这条总线上，运行时由固件/ROM 决定谁占用。
> 所以"只接 USB-OTG、不接 USB Serial/JTAG"在硬件上不存在。
> 真正要问的是：**USB-C 的 D+/D- 到底有没有接到 GPIO19/20**。

**情形 A：USB-C 的 D+/D- 接到 GPIO19/20（标准接法，绝大多数板子如此）**

- 工作态：TinyUSB CDC 跑在 **USB-OTG** 外设上，枚举为 TinyUSB 配置的 VID/PID
  （Espressif 默认 CDC 是 `303A:4001`），呈现为 `COMx`。
- 进入下载模式后：ROM 启用 **USB Serial/JTAG** 控制器，VID/PID 固定 `303A:1001`，
  呈现为**新的 `COMy`**。
- 也就是用户会看到"原来的 COM 口消失了，冒出个新 COM 口"——但**线不用拔**，还是同一个 USB-C 口。
- **上位机必须实现**：下发 `0x13` → 监听原设备移除 → 轮询等待 `303A:1001` 出现（超时 15s）
  → 用新口重连 → 才开始 esptool 写入。否则用户 100% 看到"连接失败"。
- esptool 原生支持这个流程（`--chip esp32s3` 下会自动处理 USB Serial/JTAG 枚举）。

**情形 B：USB-C 的 D+/D- 没有接到 GPIO19/20（例如 USB-C 只供电，或数据线悬空）**

- 则**整条 USB 数据通道都不存在**，PRD 5.5 选定的 TinyUSB CDC 方案（按键上行、心跳、
  配置下发、烧录）全部落空，这是比烧录流程大得多的问题，必须回到硬件层解决。
- 因此本设计**不为此情形做预案**；若真出现，属于 PRD 层面的方案返工，不是软件能绕过的。

**情形 C：板上另有一颗 USB-TTL 桥接芯片（CH340/CP2102 等）接到 UART0**

- 则下载模式也可以走 UART0，不依赖 USB Serial/JTAG。
- 但这会给普通用户增加"用哪个口"的困扰，与 PRD 6.6"干净系统即插即用"的目标不符。
- **本设计仍以情形 A 为主路径**；仅当情形 A 实测不通时，才在 `Flasher` 里加 UART0 分支作为兜底。

> **已确认（2026-10-04，owner 拿原理图确认）：USB-C 的 D+/D- 接到 GPIO19/GPIO20，
> 板上没有独立的 USB-TTL 桥接芯片。** 即**情形 A**，本设计的主路径成立。
>
> 由此冻结两组 VID/PID，上位机按它们枚举设备：
>
> | 阶段 | 占用外设 | VID:PID | 说明 |
> |---|---|---|---|
> | 工作态 | USB-OTG + TinyUSB CDC | `303A:4001` | Espressif 默认 CDC；若在 Kconfig 里改了自定义 VID/PID，此处必须同步改 |
> | 下载模式 | USB Serial/JTAG（ROM） | `303A:1001` | ROM 固定，不可改 |
>
> PRD 6.6 的"干净系统即插即用、安装包不携带驱动"在此接法下成立：
> Windows 10 1809+ / 11 对 `303A:1001`（usbser）与 `303A:4001`（WinUSB/usbser）
> 均有内置驱动支持，用户全程不需要装驱动、也不需要外部 USB-TTL。

### 7.2 AP 密码

| 项 | 值 |
|---|---|
| 冻结值（占位） | `Vb7Kq2mXv9`（10 位，混合大小写+数字） |
| 定义位置 | `CONFIG_VIBEKEY_AP_PASSWORD`（Kconfig），编译期可覆盖 |
| 说明书 | 印刷在产品说明书首页 |

> ⚠️ **上线前必须替换**为开发者统一生成的随机串。当前值只是占位，避免仓库里出现空密码。
> 已知弱点：所有设备共用同一 AP 密码，同局域网内任何人可连。彻底方案是每台设备用 MAC 派生唯一密码并打印在机身标签上——建议二代硬件做，本期按 PRD 执行。

### 7.3 凭据存储

- WiFi 密码、ASR SecretKey 全部落 **NVS**，不明文进 UART1 日志（PRD 9 章要求）。
- `0x12` 帧经 USB 串口传输时本身是明文的——这是物理层固有限制。**缓解**：载荷做轻量 XOR 混淆（密钥 = magic word），并在隐私协议中说明"配置经 USB 明文传输，请勿在不可信 PC 上配置"。
- 不在 NVS 之外（如 Flash 明文分区、日志文件）留存任何副本。
