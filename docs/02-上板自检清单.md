# VibeKey 上板自检清单

> **用途**：`port_board.h` 里的 GPIO 目前全是**占位值**，未经硬件验证。
> 本清单的目的就是在不依赖任何假设的前提下，逐项确认硬件实际接线，
> 并把结果回填到 `port_board.h`。
>
> **前置条件**：硬件组已提供真实引脚分配表（见 [01-引脚分配表.md](01-引脚分配表.md)），
> 或按本清单第 0 步自行测出。
>
> **所需工具**：USB-C 线、USB-TTL 转接板（接 UART1）、万用表或 LED 观测、
> 螺丝刀（拨动开关）、一部能连 WiFi 的手机。

---

## 0. 先测出真实接线（如果还没有引脚表）

这一版固件的所有 GPIO 都是占位的，所以**不要先假设它对**。
按下面顺序测，把结果填进 `port_board.h`：

| 测什么 | 怎么测 | 记下 |
|---|---|---|
| 按键 | 万用表通断档，一颗颗测按键两端各接到哪颗 GPIO | K1–K7 的 GPIO |
| 按键是否低有效 | 按下时测 GPIO 对 GND 是否导通 | 是 → 低有效（固件已按此假设） |
| 编码器 A/B | 旋钮时测哪两颗 GPIO 之间有 90° 相位跳变 | A、B 的 GPIO |
| 编码器按下 | 按下旋钮测哪颗 GPIO 对 GND 导通 | SW 的 GPIO |
| 蓝灯 / 红灯 | 看 LED 背面走线，或从原理图找限流电阻另一端 | 两颗 LED 的 GPIO |
| UART1 | 找原理图上标 TX/RX 且**不是** GPIO43/44 的两颗 | TX、RX 的 GPIO |
| 麦克风 | 确认是 I2S（三根线 BCK/WS/DIN）、PDM（两根）还是模拟（一根进 ADC） | 类型 + GPIO |

> ⚠️ **GPIO 26–32 是模组内部 SPI Flash/PSRAM 用的，禁止分配**。
> GPIO 43/44 是 UART0（ESP-IDF 日志口），不要占用。
> GPIO 19/20 已被 USB 数据线占用（D-/D+）。

## 1. 烧录

```bash
cd firmware
powershell -ExecutionPolicy Bypass -File ..\tools\idf.ps1 -p COMxx flash monitor
```

**预期**：烧录成功，monitor 里出现
```
I (xxx) vibekey: VibeKey 固件启动，版本 0.1.0
I (xxx) port: 移植层就绪
```

**同时**，另开一个串口助手接 **UART1**（波特率 115200 8N1），应看到：
```
STATUS:PORT_READY
STATUS:BOOT,FW=0.1.0
STATUS:AP_START,FW=0.1.0,SSID=VibeKey-XXXX
```

- [ ] 烧录成功
- [ ] UART1 收到 `STATUS:PORT_READY`
- [ ] UART1 收到 `STATUS:BOOT,FW=0.1.0`
- [ ] SSID 后缀 `XXXX` 与设备 MAC 后 4 位一致（大小写无所谓）

> `STATUS:PORT_READY` 是移植层自报的，PRD 里没有，是开发期用来确认
> UART1 通路本身是好的。最终版可以去掉。

## 2. LED 状态机（对应 PRD 5.1）

空 NVS 上电 → 设备进 AP 态。

| 检查项 | 预期现象 | 结果 |
|---|---|---|
| 上电瞬间 | 蓝、红**同时常亮**（BOOT 态，≤2s） | ☐ |
| 随后进入 AP | **红蓝交替闪烁**，周期约 1s（前 500ms 蓝亮，后 500ms 红亮） | ☐ |
| 交替是否互斥 | 任一时刻只有一颗亮，不会两颗同时亮 | ☐ |

- [ ] BOOT 态双灯常亮可见
- [ ] AP 态红蓝交替、互斥

> 如果两颗灯的行为**对调**（该蓝亮时红亮），说明 `port_board.h` 里
> `VK_BOARD_LED_BLUE_GPIO` 和 `VK_BOARD_LED_RED_GPIO` 填反了。
> 如果只有一颗亮，另一颗的 GPIO 填错了或 LED 极性相反。

## 3. USB CDC 枚举（对应 PRD 5.5 / 6.1）

| 检查项 | 预期 | 结果 |
|---|---|---|
| 设备管理器 | 出现一个 COM 口 | ☐ |
| 该设备属性 → 详细信息 → 硬件 ID | 含 `VID_303A&PID_4001` | ☐ |
| 是否需要装驱动 | **不需要**，Windows 10/11 自带 usbser.sys | ☐ |

- [ ] 枚举出 COM 口
- [ ] VID/PID 是 `303A/4001`
- [ ] 无需手动装驱动

> 如果 PID 不是 `4001`，检查 `main/tusb_config.h` 有没有被改动，
> 以及 `port_esp32.c` 里 `VK_USB_PID` 的定义。
> 如果完全枚举不出来，先确认 USB-C 的 D+/D- 确实接到了 GPIO19/20。

## 4. 按键字符（对应 PRD 5.4）—— 最关键的一项

用串口助手打开第 3 步那个 COM 口（波特率随意，CDC 虚拟串口不关心波特率），
然后逐个按按键。

| 操作 | 预期收到的字节 | 结果 |
|---|---|---|
| 按 K1 | `1` (0x31) | ☐ |
| 按 K2 | `2` | ☐ |
| 按 K3 | `3` | ☐ |
| 按 K4 | `4` | ☐ |
| 按 K5 | `5` | ☐ |
| 按 K6 | `6` | ☐ |
| 按 K7 | `7` | ☐ |
| 旋钮**顺时针**一格 | `+` (0x2B) | ☐ |
| 旋钮**逆时针**一格 | `-` (0x2D) | ☐ |
| 按下旋钮 | `0` (0x30) | ☐ |

**接着测可靠性**（PRD 5.4 验收口径）：

- [ ] 快速连按 K1 共 100 次，收到**恰好 100 个** `1`（不多不少）
- [ ] 长按 K1 3 秒，只收到**一个** `1`（不连发）
- [ ] 慢速旋转旋钮一整圈，`+` 的数量 = 旋钮标称档位数
- [ ] 不要出现"转一格出两个方向字符"（比如同时收到 `+` 和 `-`）

### 异常对照表

| 现象 | 原因 | 怎么修 |
|---|---|---|
| 某个键完全没反应 | 该键 GPIO 填错，或按键另一端没接 GND | 回第 0 步重测该键 |
| 按一次出多个字符 | 该 GPIO 有硬件抖动且消抖不够 | `port_board.h` 给该键加硬件 RC，或临时把 `VK_DEBOUNCE_MS` 提到 20 |
| 总要按很重才有反应 | 内部上拉没生效 / 按键接了上拉而非下拉 | 检查 `port_esp32.c` 的 `io.pull_up_en` |
| 旋钮方向反了 | A/B 相接反了 | 对调 `port_board.h` 里 `VK_BOARD_ENC_A_GPIO` 和 `VK_BOARD_ENC_B_GPIO`（**不用改代码**） |
| 旋钮转一格出两个字符 | 消抖不足或 A/B 相位噪声 | 见 `app/key_fsm.c` 的正交解码；先确认没接触不良 |
| 同一颗键收到两个不同字符 | 两颗键的 GPIO 填成同一个了 | 查 `port_board.h` 有没有重复值 |

> **旋钮方向反了不要改代码**——这是 `port_board.h` 存在的意义：
> 硬件变动只改一个文件，`app/` 一行不动。

## 7. 已知当前固件**做不到**的事

列出来是为了避免把这些误判成 bug：

| 做不到 | 原因 | 现象 |
|---|---|---|
| 配网 | `p_wifi_start_ap` / `p_wifi_start_sta` 是 TODO | 连不到 `VibeKey-XXXX` 热点；设备停在 AP 态不死机 |
| 语音 | `p_mic_init` / `p_asr_start` 是 TODO | 按 K7 无反应；ASR 失败只上告 `WARN=ASR_UNAVAILABLE`，不进 ERROR 态 |
| 写固件 | 上位机的 `Flasher` 还没实现 | 见下面第 8 步 |

### ✅ 但"进入烧录模式"这条是通的，值得专门测

`0x13` 指令的整条链路已经完整，不依赖 WiFi/ASR：

```
上位机点"进入烧录模式"
  → USB 发 0x13 + magic word
  → vk_app_on_usb_bytes 解码
  → vk_cmd_handle 四道校验（USB 通道 / 长度 8 / magic / 非 ERROR 态）
  → 下发 STATUS:DOWNLOAD
  → nvs_commit
  → esp_restart() 进下载模式
```

**这是验证设计文档 §7.1"COM 口跳变"方案的最好机会**，虽然真正写固件那一步还做不了。

> 这条链路的**软件部分已有测试背书**：`firmware/test/test_app.c` 的
> `app_dfu_channel_rule` 套件验证了"USB + 正确 magic → 调用 reboot"和
> "WiFi + 正确 magic → 不 reboot"两种情况（39 项断言之一，全部通过）。
> 未覆盖的只剩 `p_reboot()` 那三行（需要真实硬件才能验）。

**测法**：第 4 步通过后，用上位机（勾选"模拟设备"取消，选真实 COM 口，点连接），
再点"进入烧录模式"并在二次确认框点"是"。

| 检查项 | 预期 | 结果 |
|---|---|---|
| UART1 | 收到 `STATUS:DOWNLOAD,FW=0.1.0` | ☐ |
| 设备管理器 | 原 COM 口消失，冒出**新** COM 口 | ☐ |
| 新设备硬件 ID | 含 `VID_303A&PID_1001`（ROM 的 USB Serial/JTAG） | ☐ |
| USB 线 | **不需要拔插** | ☐ |
| 上位机日志 | 显示"下载模式就绪，串口已跳变为 COMxx" | ☐ |

如果超时报"等待下载口超时（15s）"，说明板子没重启或 USB Serial/JTAG 没枚举出来——
这本身也是个需要知道的硬件事实。

## 8. 通过标准

第 2、3、4 步全绿 = **M1 验收通过**，可以进入 M2（WiFi 配网闭环）。

PRD 对 M1 的原始要求是：
> LED 状态机 + UART1 状态上报 + 按键消抖 + USB CDC 枚举，
> 可被串口助手/上位机 demo 看到按键字符。

本清单逐条覆盖了这四项，另外第 7 节的端口跳变是额外收获——
它验证的是 PRD 6.3 烧录入口的地基，提前测到能省掉 M3 的一次返工。
